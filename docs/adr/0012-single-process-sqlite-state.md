# Single-process SQLite state

The mutation journal and JWT token registry support one server process on one host with persistent local SQLite, keeping the guarantee within the deployment model we have validated. Multi-instance operation is intentionally out of scope: separate instance databases do not share mutation deduplication or token revocation, and shared or network SQLite storage is unsupported. Revisit scale-out only when required and after separately approving a shared transactional backend and deployment model.

HTTP operation ownership is tied to the JWT `jti` (tokens without a `jti` use a digest of the exact verified JWT). A reissued JWT is a different owner and cannot replay the previous token's results or bypass a retained reservation. Rotating the upstream key on the same JWT record does not change ownership (see [ADR-0011](0011-server-side-token-registry.md)). `athlete_id` and an API-key hash do not establish continuity across tokens. Stable identity across reissue remains out of scope.

Unknown mutation outcomes remain blocked and retained in SQLite. The server has no public MCP tool or admin endpoint to inspect or resolve them; adding one is intentionally excluded until its API, authorization rules and audit behavior are separately approved. Operators must investigate the upstream system out of band. They must not clear an unknown record or retry its mutation without evidence that the original write had no effect.

## v3.0.0 implementation

- Both standard modes require a local `MCP_STATE_DB_PATH` and a persistent `MCP_STATE_ENCRYPTION_KEY` (32 bytes encoded as hex). Both use the mutation journal; HTTP also uses the token registry in that database. MCP transport sessions and browser sessions are not persisted there. Library embeddings can use non-durable state. Legacy JSON history is not imported.
- SQLite uses WAL and `synchronous=FULL`. On Unix the database and SQLite sidecars must be regular files and are kept at mode `0600`. The database is not encrypted wholesale: journal scope, fingerprint and owner are hashed, completed results are encrypted with AES-256-GCM using the state key and bound to their scope, and registry credentials use the separate JWT master-key-derived encryption key. Registry metadata remains readable; protect the files and backups.
- The journal scopes an operation by normalized upstream base URL, athlete ID and idempotency token, then commits a reservation before dispatch. A retained completed result is replayed without another write only for the matching request fingerprint and owner (STDIO uses its configured scope, without a JWT owner). Completed results expire after 24 hours. Older SQLite records without upstream/athlete scope can block a matching token while retained but cannot supply a replay.
- In-flight records become unknown at startup. A write that may have run without a recorded completion stays blocked across restarts; unknown records do not expire and are not evicted to make room. This protects retries of the same retained operation key, not arbitrary duplicate writes using a new key.
